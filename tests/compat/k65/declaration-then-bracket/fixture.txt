**A `[ … ]` block on the line after a declaration is a top-level evaluator
block, in both compilers.**  The golden's `13 04 0F` is `BASE + STEP`, `COUNT`
and `MASK` - three names three separate blocks assigned - and K816's
`expected.hex` carries the same three bytes.

That is a compatibility row now and was a defect until G10a.  K816's expression
layer has a postfix `[` that K65's has not, because K816's symbolic subscripts
are one (`COMP[2]`, `TASKS[.slot]`), and a postfix in a newline-insensitive
language reaches the next line: `const BASE = 0x10` above `[ STEP = 3 ]` parsed
as `BASE = 0x10[STEP = 3]` and reported `K816-E0001`.  A valid K65 program
reaching a *generic parse error* is exactly what decision 0 forbids, and the
manifest row `newline-subscript` carried it as `open` from G5 until here.

The fix is one token: the postfix `[` binds to its base with no space between,
which is the rule `field_name` has had since B for the same reason one level
down - `X = FOO` above a `.LT+1` must not be one field access.  It is K816's
postfix, so the rule is K816's to make; the *evaluator's* `EvElem [ … ]` is
K65's own and stays newline-insensitive, because there `t` above a `[0]` is
`t[0]` in the original too (`evelem-index`).

The cost is that `COMP [2]` with a space is no longer a subscript.  No source
in this repository writes it, and the same rule already applies to `.field`.

Three shapes, because the reading was per-shape and each ends in a different
place: `const NAME = value`, `var NAME = address`, and a `var` whose one
bracket is already spent on a span.  The last is the one that says the fix is
not "a declaration may take only one bracket" - `var span[4]` has taken its
bracket and the block below it still has to be a block.

One difference from the oracle image and it is the linker's: the original opens
with `4C 06 20`, a `JMP main` stub K816 does not emit because ld65 places the
entry, so everything after it sits three bytes lower here and `a = answers`
reads `$2000` rather than `$2003`.  Every generated byte agrees.
