Since G2: eighteen diagnostics, and **no `K816-E0001`** - which is the task's
done criterion.  Three things went with G1's twenty-one.

  - The one syntax error was this fixture's own bug, not a compatibility gap.
    It wrote the image scan word as `8 > 8 v`; every attested source writes
    `8>` with no space, and so does `image_scan`.  The original tolerates the
    spaced form - re-running `oracle.sh` over the corrected source produced a
    byte-identical `oracle.hex`, only the checksum line moved - and the
    manifest's `topelem-image` row says so.  K816 does not, and no rule is
    worth spending on a spelling no source uses for a construct that is
    refused anyway.
  - `i+ d-` - SEI then CLD - used to parse as the arithmetic `i + d` followed
    by a statement starting `-`, which reached the AST builder as a register
    named `i` and answered `K816-E0900`.  The ERROR node above hid it: the
    builder suppresses internal reports once recovery has fired, so fixing the
    image line is what exposed it.  Two changes close it, both in
    `postmortem.md` §G.1.16: `i` and `v` leave the shared register token, since
    they are flags and no rule but `hla_flag` wants them; and the flag
    statements a store swallowed are peeled back off in the AST builder, the
    way decision 16's leading call already is.
  - `s = x = 0xFF` followed from it: `s` had been reading as part of that
    swallowed expression rather than as the stack pointer.

The two `K816-K65-0003` are `bank core`, refused in both units (decision 10),
and `K816-K65-0001` is `image` (decision 12's neighbour, G6's to keep refused).
The `K816-E0101` are the TIA register names, which the original's A2600 system
script declares before the first unit and K816 has no equivalent of; the
`K816-E0104` are `lda` immediates in `inline` sections no annotated caller has
reached yet.  Neither is a compatibility gap, and both are the environment's
rather than the language's.

A whole K65 program, written for this corpus, in two units.

Every other fixture here isolates one claim. This one exists because a real
source does not: it mixes `bank`, a `var` comma list with the `?` marker,
`inline` sections called by name, a bare call and a store on one line
(`wsync HMOVE = a`), `align`, `image` with `tiles`, `for … eval` behind an
`evaluator [ ]` transform, and evaluator brackets in three positions —
operand, data entry and `for` bound. Constructs that each parse in isolation
can still collide, and this is where that shows.

It replaces a program vendored from the original K65 distribution. That copy
came with no licence and no redistribution permission, so it is gone; this is
independently authored, and `sheet.bmp` with it — a 32×16 24-bpp bitmap whose
pixel at column *x*, row *y* is black when bit *x* mod 8 of ⌊*x*/8⌋ + *y* is
set, so each of its four tiles carries a different, checkable bit pattern.

Three things it taught while being written, none of them in any document:

  - `tiles` is a keyword, so `image tiles …` does not parse — an image's name
    cannot be `tiles`.
  - a `for` bound is a `Number`, and a `const` is an `Ident`, so
    `for i = 0 .. RAMP_LENGTH` does not parse and `0 .. [ RAMP_LENGTH ]`
    does.
  - the original aborts without a diagnostic on all three, which is why
    `oracle.sh` prints the compiler's log when a build it expected to succeed
    fails.

What remains falls at G4 (the brackets and `for … eval`) and G6 (`image`,
which stays refused, and the `evaluator [ ]` transform, which lands). Both
units are compiled as entries, so both report.
