`charset` and an `evaluator [ ]` entry in one data block.

The `evaluator [ ]` entry is the form decision 5 recognised and refused
pending G0's oracle answer.  The answer is measured in
`tests/compat/k65/eval-forms/`: `evaluator [ code ]` precompiles a program into
the *section's* evaluator, and every byte the section afterwards **generates** -
a `for ... eval` value, a character of a string through `charset`, a byte
pulled from a `binary` or an image tile - is passed through it as `x`.  Literal
data entries are not touched.  It is a per-byte transform over generated
bytes, which is cheap, so decision 5's refusal is lifted and G6 implements it.

Since G6 the transform runs, and the `K816-E0101` for `SCALE` stays - it is
K816's one deliberate divergence on this construct rather than a leftover.

`evaluator [ SCALE = 2 ]` is a transform whose *value* is the assignment, so
every byte the section generates becomes 2 in the original, and `SCALE` is
readable below it because the transform runs in the global evaluator
environment.  K816 runs it against the environment recorded at its own line,
in a copy per byte, so nothing escapes and `[SCALE]` reads a name nothing gave
a value.

The reason is structural and it already had a precedent: a transform runs
during *resolution*, and resolution runs twice - once for analysis, once for
lowering - so an assignment that escaped would happen twice or would depend on
which walk ran.  `for … eval` carries the same deviation for the same reason,
and G6 made the two one mechanism.  `data-evaluator-entry` is the row.

Nothing attested assigns from a transform, and a transform that does replaces
every byte with one value anyway, which is not a thing a program wants.

Before G1 there were three diagnostics, the extra one a `K816-E0101` for the
undeclared name `evaluator` - the grammar had no rule for the entry, so the
keyword arrived as a data value.  Before G4 there were two `K816-E0201`,
because no bracket anywhere was evaluated.
