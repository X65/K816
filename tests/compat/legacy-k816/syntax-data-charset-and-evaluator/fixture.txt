`charset` and an `evaluator [ ]` entry in one data block.

The `evaluator [ ]` entry is the form decision 5 recognised and refused
pending G0's oracle answer.  The answer is measured in
`tests/compat/k65/eval-forms/`: `evaluator [ code ]` precompiles a program into
the *section's* evaluator, and every byte the section afterwards **generates** -
a `for ... eval` value, a character of a string through `charset`, a byte
pulled from a `binary` or an image tile - is passed through it as `x`.  Literal
data entries are not touched.  It is a per-byte transform over generated
bytes, which is cheap, so decision 5's refusal is lifted and G6 implements it.

Today, after G4: one `K816-E0201` for the `evaluator [ ]` entry, and one
`K816-E0101` for `SCALE`.  The second is a *consequence* of the first and moves
with it: the evaluator runs every bracket in source order, and the one bracket
in this file it does not run is the deferred entry - so the name that entry
assigns is never assigned, and the `[SCALE]` below it reads a name nothing
gave a value.  G6 closes both with one change.

Before G1 there were three diagnostics, the extra one a `K816-E0101` for the
undeclared name `evaluator` - the grammar had no rule for the entry, so the
keyword arrived as a data value.  Before G4 there were two `K816-E0201`,
because no bracket anywhere was evaluated.
