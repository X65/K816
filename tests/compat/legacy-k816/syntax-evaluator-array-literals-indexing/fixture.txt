`arr = [10, 20, 30]` followed by `arr[1]`.

The legacy K816 read this as an array literal.  The original has no array
literal: `Number -> [ EvalCode ]` and `EvalCode`'s comma is the *pop* operator
(`compiler.inc:328,359-360`, opcode 1), so `[10, 20, 30]` is 30, and the value
`arr[i]` indexes has to be a section.  A row where importing the legacy
fixture as truth would have enshrined a construct K65 never had, which is what
decision 2 is for.

Today, after G10a: two `K816-E0001` and two `K816-E0101`.  The construct that
fails is the same one - `[` cannot open a value inside an evaluator expression,
because there is no array literal to open - and the two `K816-E0101` are `A`
and `B` read in `main`.  They follow from the first two: a bracket the parser
had to recover inside is not evaluated at all, so the block that would have
assigned those names never ran.

There were three `K816-E0001` between G4 and G10a, and the one that went was a
*cascade*, not a construct.  Recovery from the stray `[` used to restart at
`A = arr[1]` and fail again at the following line, because `arr` followed by a
`[` on the next line was a subscript to reach for.  G10a made the K816 postfix
`[` bind to its base with no space between (`newline-subscript`), so recovery
now spans to the closing `]` in one error node.  The construct this fixture is
about is unchanged; only how far the parser stumbles after it.

Before G4 the last four were `K816-E0201`, one per unevaluated bracket; before
G1 the whole file was one `K816-E0001` and three `K816-E0201`, because a
bracket held a single expression rather than a statement list and recovery from
the stray `[` swallowed the two entries after it into one error node.

`arr[1]` and `index(arr, 2)` themselves still parse -
`tree-sitter-k65/test/corpus/expressions.txt`, "Evaluator indexing" - and each
would be `K816-E0201` in a file that reached them, because what a bracket
indexes is a section's assembled bytes and those are G6's.
